# Tooluse Skills

这是一组把验收、执行、审查、改动范围约束、自有服务器部署、项目文档体系，以及思考方法选型与自我认识访谈写成可复用规则的 Skills。它们约束证据怎么产生、怎样冻结、由谁裁决，也把真实部署中重复出现的安全边界整理成清单；不替代产品判断、团队权限或真实用户验收。八个自建 Skill 加五个第三方逐字副本，共十三个目录，全部从本仓库安装。它们平铺在 `skills/` 同一层，第三方的在自己目录里带 `SOURCE.md`。

## 这是什么

- `acceptance-author`：在实现前起草、反证并冻结可证伪的验收判据。
- `evidence-bound-executor`：按冻结契约实施，并交接能被独立复核的证据。
- `evidence-led-reviewer`：从仓库事实重建候选实现，审判据、查盲区并按实际影响定级。
- `scope-bound-editor`：**A 管改动边界**——只改请求点名的面、兼容层必须已有人在付代价、复用而不并行实现、不解决问题的一般形式、界内穷尽到每一处兄弟；**B 管产物内容**——只写最终状态不写被否掉的方案、一个事实一个家、不快照会变的值、行为改了扫抄写点。常驻，不挑批次。
- `deploy-to-self-managed-server`：用专用密钥、强制命令、固定主机密钥、严格发布标识、内容校验、原子切换、回滚、凭据隔离和版本健康检查九条判据审查自有服务器发布。
- `project-doc-system`：从零建起文档骨架，按触发条件生长，用路由式索引控制上下文成本，并给可判定的不变量配带负向控制的门禁。
- `thinking-toolkit`：按用户卡在问题层、理解层、可信层、方案层还是抉择层，从十个思考方法里选定一个，并把结论收口到适用条件与可执行的第一步。
- `life-design-interview`：用长程多轮追问把散落经历拼成《个人天赋使用说明书》或《个人人生设计蓝图》，带明确的心理负荷边界。

全部可安装到用户级或项目级 Skills 目录。不支持 Skills 时，审查角色使用 `evidence-led-reviewer/assets/reviewer-role-prompt.md`，其余流程直接使用对应 `SKILL.md`。

拆分前记录的 contract SHA（包括 `dd56ff6`、`3acdf0d`、`4b8a1b8`、`f3129ba`）指向 `Andrew-JX/mj-portfolio` 的历史；本仓库经过 subtree 重写后的 SHA 与它们不对应。

## 该用哪一个

十三个目录平铺在 `skills/`，**不要全部读进来**——按下表只取命中的那一行。这张表是路由，不是清单。

| 我现在卡在 | 用 | 来源 |
|---|---|---|
| **说不清要做什么**，需求还很松 | `grill-me`（手动喊）/ `grilling`（模型自选） | 第三方 |
| 想清楚了，**要定「做完是什么样」** | `acceptance-author` | 自建 |
| 判据已冻结，**开始实施并交接证据** | `evidence-bound-executor` | 自建 |
| 有人交了东西，**要独立复核** | `evidence-led-reviewer` | 自建 |
| **改的是现成的东西**，怕越界或漏抄写点 | `scope-bound-editor` | 自建 |
| **有个 bug 查不出来**，或性能回归定位不到 | `diagnosing-bugs` | 第三方 |
| 要**换一个模型的窗口**拿独立性，或把一段活外包出去 | `codex-cli` | 第三方 |
| 改动大 / 要并行 / **需要一份没动过的 baseline 对比** | `worktree-pr` | 第三方 |
| 要**发布到自有服务器** | `deploy-to-self-managed-server` | 自建 |
| 新项目**要建文档体系** | `project-doc-system` | 自建 |
| **不是工程问题**：概念看不懂、调研、核查、纠结选哪个 | `thinking-toolkit`（它自己再路由十个方法） | 自建 |
| 想弄清**自己**擅长什么、想过什么样的生活 | `life-design-interview` | 自建 |

**`diagnosing-bugs` 的 description 只有 156 字符而正文有 8.5k**，它很可能该触发时不触发——它是第三方逐字副本，本仓库不改它，靠这张表补上。

## 交付流程

**交付流程就是这套 Skill 包本身，没有另一张步骤表。** 早期版本有一张十一格的流程图，已经不再是本仓库的依赖——步骤表会随流程简化而变，而 Skill 只描述自己那个环节要守什么，流程怎么变都不用回来改它。正文里已经不出现步骤编号，只说环节名。

| 环节 | 用哪个 | 常驻？ |
|---|---|---|
| 定判据 | `acceptance-author` | 按影响开 |
| 实施并交接证据 | `evidence-bound-executor` | 按影响开 |
| 独立核验 | `evidence-led-reviewer` | 按影响开 |
| 改动范围与产物措辞 | `scope-bound-editor` | **常驻** |

前三个是加码包：判高影响看五条——**会不会伤到用户、碰不碰数据与权限、有没有安全面、爆炸半径多大、坏了能不能恢复**。低影响的活写一句可证伪的判据、完成后查真实 diff 就够。**发布本身不等于高影响**，它只触发一次影响评估，不自动升档。

`scope-bound-editor` 不在这个开关上——它的成本接近零，任何一次改动都适用。它填的是「低影响日常改动」那一格：那一格刻意不设防（因为设防就会重到被绕过去），代价是顺手重构、讨论残留进产物、同一事实多处副本和漏抄写点这四类事故。

其余四个（`deploy-to-self-managed-server`、`project-doc-system`、`thinking-toolkit`、`life-design-interview`）不接在这条链上，各自按触发条件独立使用。

**两件事没有自动触发器**：开工前先用自己的话写清目标与硬约束，以及最后自己拍板并讲得出改了什么。它们靠人想起来，而它们恰好是防止判据本身写错的两道关。这个结构性事实和流程有几步无关。

变更账本里 2026-08-08 那行写的「走完十格」是当时的口径。账本是历史记录，不追溯改写。

## 验证到什么程度

**这里不设状态词。** 留在仓库里的就是还没被判死的；判断为不需要的直接删掉，理由记进变更账本。位置本身就承载了这个信息，不另设一套标签——**同一个事实存在于多处可独立编辑的地方，漂移是静默的**，而手工维护的状态标签正是那种会自己变错、且出错时没有任何东西会失败的东西。

下面每条写的是**还没有被证明的那一半**。

- `acceptance-author` / `evidence-bound-executor` / `evidence-led-reviewer` —— 三个交付 Skill 有完整证据链，见下一段。仍未测的是触发准确率。
- `deploy-to-self-managed-server` —— 九条判据来自两次独立上线的交集，其中第 9 条是两次实现都漏掉、靠清单比对才浮出来的。但**清单式 Skill 本身尚未在下一个项目触发过**；底层机制的证据不等于 Skill 的复用与触发证据。
- `project-doc-system` —— 脚手架、索引门禁与负向控制已在隔离临时项目跑通，并对两个真实项目做过只读探测，但**没有任何项目按它建起过完整文档体系**。「文档体系活下来了」要几个月和多次需求变更才验证得了。
- `thinking-toolkit` —— 2026-08-25 新增。真实调用只有一次：用方法 02（双层解释法）解释本仓库本身，路由判断、两层结构与三样收尾都按 `SKILL.md` 执行。两项减损：调用者是作者本人，且发生在写出它的同一个会话里。
- `scope-bound-editor` —— 2026-08-25 新增，**零调用**。规则形状多数来自两个外部 skill 的改写，本人事故只贡献了其中四条反例。**这是包里唯一常驻的 Skill，也是自建里正文最长的（5.2k 字符）——暴露面最大和证据最少落在同一个对象上。** 它的效果是弥散的（措辞变好），比其余 Skill 更难取证；可测的做法是数它那几类形状在 diff 里的出现次数，尚未做。
- `life-design-interview` —— 2026-08-25 新增，**零调用**。`references/life-design.md` 有一节标〔补写〕，是原始材料缺页后按同一框架补的，不是原文。

`thinking-toolkit` 和 `life-design-interview` 与其余六个不同源：规则不是从本人事故里长出来的，而是把一组外部方法整理成路由与边界，因此连「幸存者偏差」那条部分缓解也不适用——**它们的失效样本一个都还没有**。

三个交付 Skill 已在 `family-finance` 的 1B、2A、2B 真实批次形成完整证据链：历史会话归档能定位到各自 `SKILL.md` 的读取、紧随其后的合同冻结 / 候选实施 / 独立复核动作，以及对应合同和 candidate。三批分别经历 1、6、1 轮审查退回，判据回退均为 0；2B 真实拦下了「浏览器断言全过，但 Windows 根命令因进程清理超时退出 1」的假绿灯。这不是根据方法相似性倒推。

**删除只能由真实使用结果触发**，不能因为规则写完、脚本跑通或一次自审就删，也不能因为一时没想起来用就删。反过来，真实条件下具备可用条件却零次调用，同样是结果、不是空白——那是删除的理由。

## 第三方 Skill

`skills/` 下有五个目录是**上游的逐字副本**，不是本仓库写的。它们和自建 Skill 平铺在同一层（嵌套会让 Skill 发现找不到），各自目录内带 `SOURCE.md` 标出处与钉住的 SHA。

| Skill | 干什么 | 上游 | 许可证 |
|---|---|---|---|
| `diagnosing-bugs` | 难 bug 与性能回归的诊断循环：先建反馈环 → 复现并最小化 → 假设 → 插桩。完成判据是「一个能稳定变红的紧环」 | [mattpocock/skills](https://github.com/mattpocock/skills) | MIT |
| `grilling` | design tree + frontier 分轮提问，把一个很松的想法逼成一组能落地的决定 | 同上 | MIT |
| `grill-me` | `grilling` 的转发壳，两个必须一起装 | 同上 | MIT |
| `codex-cli` | 什么时候值得把活交给 Codex CLI，以及怎么定模型、effort、沙箱权限和怎么读回结果 | [scarletkc/agents](https://github.com/scarletkc/agents) | Apache-2.0 |
| `worktree-pr` | 一个任务值不值得单开 worktree；从集成分支切、主工作树保持可用、交付前与未动过的 baseline 对比 | 同上 | Apache-2.0 |

**硬规矩：这五个目录本地永不编辑。** 钉住 SHA 且不编辑，把「静默分叉」降级成「可检测的陈旧」。要覆盖上游行为就写进自建 Skill，不改那边。

许可证与 NOTICE 全文见 [skills/THIRD-PARTY.md](skills/THIRD-PARTY.md)。跑 `scripts/check-vendor-freshness.sh` 核对是否已分叉；`.github/workflows/vendor-freshness.yml` 每周一自动跑一次，有分叉就开 issue，**只报告不自动更新**。

两处自建 Skill 用了上游的规则形状但没有收录原文，属于改写而非副本，出处记在各自文件末尾：`scope-bound-editor`（来自 scarletkc 的 `scoped-change` 与 `ux-writing`）、`acceptance-author` 第 10 项（来自 mattpocock 的 `tdd` 反模式一节）。**`tdd` 本身没收**——它的「先写失败测试」与 `scope-bound-editor` A4「逻辑定了再钉测试」冲突。

## 已知边界

### 闭环

自建规则的输入来自同一个人的项目、窗口和记忆。这套体系可以带着完整证据链整体一致地错，而系统内几乎没有信号源能发现。

**2026-08-25 起这条被部分打开，但打开得比看上去少。** 十三个目录里有五个是第三方逐字副本，另有两个自建 Skill（`scope-bound-editor`、`acceptance-author` 第 10 项）的规则形状改写自外部。这是第二个外部输入源，**但它验证的东西很有限**：它带来的是另外两个人的事故清单，能补上「我没撞过所以没写」的空缺，**不能验证这套体系整体是不是错的**——那需要现实来反驳，不是需要更多规则。

已知的两个真外部输入仍然只有：**用真实数据使用运行中的产品**，以及**真实工作**（它给出的第一个读数是负的——`work-skill` 被判死）。

### 幸存者偏差

每条规则都对应一次被抓住的事故。没被抓住的事故不产生规则，也没有机制让它们浮出来。`blind-spots.md` 是形状级泛化，是对这条的部分缓解，不是解决。

### 执行侧依从性已有真证据，人侧仍未稳定

`family-finance` 历史归档已经证明三个交付 Skill 确实被读取并紧接着执行，这解决了「方法做过，但 Skill 包是否触发」的证据缺口。它仍不能证明每次该触发时都会触发，更不能替代人侧那两件事——开工前先自己写清目标，以及最后自己拍板并讲得出改了什么。它们没有自动触发器，仍靠人想起来，而它们恰好是防止判据本身写错的两道关。

### 真实触发已经发生，触发准确率仍未测——而且这条边界在变差

三个交付 Skill 已有真实正向触发样本，而且历史用户没有逐字输入带连字符的 Skill 名称，Agent 仍读取了正确的 `SKILL.md`。但这只能证明「触发过」，没有未触发对照、误触发样本和固定任务集，仍算不出召回率与准确率。

**Skill 数从 6 涨到 13，这条边界的严重性跟着涨，文本此前一直没动。** 具体地：

- 八个自建 Skill 的 description 格式一致（一句说清是什么 + `Use when` 从句），但长度从 284 到 749 字符不等。长的那几个从句多，理论上更容易误触发，**但这只是推测，没有测量**。
- `diagnosing-bugs` 是反过来的：正文 8.5k 而 description 只有 156 字符，很可能该触发时不触发。它是第三方逐字副本，本仓库不改它，靠「该用哪一个」那张路由表补。
- 十三个 description 合计约 5.7k 字符，**每次会话常驻**；正文合计约 62k，按需加载。路由表存在的另一个理由就是别让人把 62k 全读进去。

## 不适用范围

一晚上内、单模块、可回滚且不涉及安全、数据、权限或发布的小活，验收、执行与审查 Skill 都不触发。写一句可证伪的判据、完成后检查真实 diff 即可。

**`scope-bound-editor` 是这条的例外，它没有下限**——正是这一格里的改动最容易顺手重构、把讨论残留写进产物。它的成本接近零，省掉它没有收益。

`deploy-to-self-managed-server` 覆盖静态站与全栈两种发布形状，不覆盖未经独立评审的数据库回滚、跨服务编排，以及本仓库未验证过的托管平台。风险高时不因改动小而跳过完整流程。
