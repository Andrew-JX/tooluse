# Tooluse Skills

这是一组把验收、执行、审查、自有服务器部署、项目文档体系，以及思考方法选型与自我认识访谈写成可复用规则的 Skills。它们约束证据怎么产生、怎样冻结、由谁裁决，也把真实部署中重复出现的安全边界整理成清单；不替代产品判断、团队权限或真实用户验收。七个 Skill 全部从本仓库安装。

## 这是什么

- `acceptance-author`：在实现前起草、反证并冻结可证伪的验收判据。
- `evidence-bound-executor`：按冻结契约实施，并交接能被独立复核的证据。
- `evidence-led-reviewer`：从仓库事实重建候选实现，审判据、查盲区并按实际影响定级。
- `deploy-to-self-managed-server`：用专用密钥、强制命令、固定主机密钥、严格发布标识、内容校验、原子切换、回滚、凭据隔离和版本健康检查九条判据审查自有服务器发布。
- `project-doc-system`：从零建起文档骨架，按触发条件生长，用路由式索引控制上下文成本，并给可判定的不变量配带负向控制的门禁。
- `thinking-toolkit`：按用户卡在问题层、理解层、可信层、方案层还是抉择层，从十个思考方法里选定一个，并把结论收口到适用条件与可执行的第一步。
- `life-design-interview`：用长程多轮追问把散落经历拼成《个人天赋使用说明书》或《个人人生设计蓝图》，带明确的心理负荷边界。

七个 Skill 可从本仓库安装到用户级或项目级 Skills 目录。不支持 Skills 时，审查角色使用 `evidence-led-reviewer/assets/reviewer-role-prompt.md`，其余流程直接使用对应 `SKILL.md`。

## 交付流程（背景，不是依赖）

这些 Skill 最初是在一套交付流程里长出来的。**它们不依赖那套流程**：每个 Skill 只描述自己那个环节要守什么，用不用流程、流程有几步，都不影响它能不能单独使用。

- 一个人写代码、没有任何流程 → 照样可以只用 `acceptance-author` 写一句可证伪的判据。
- 团队已有自己的 code review 流程 → `evidence-led-reviewer` 直接当审查清单用，不要求你改流程。
- 任何需要「先说清做完是什么样，再动手」的活 → 三个都适用，和交付无关。

下面这张表只是背景说明，让你知道这些规则当初在解决什么位置的问题。**它正在被简化，步数会变**，权威定义在 `Andrew-JX/mj-portfolio` 的 `src/data/deliveryFlow.zh.ts`，以那份为准。Skill 正文里已经不出现步骤编号，只说环节名（判据 / 实施 / 核验 / CI 门 / 裁决），所以流程怎么变都不用回来改 Skill。

| | 步骤 | 谁做 |
|---|---|---|
| ① | 先自己写三分钟 | 人（无自动触发器） |
| ② | 摸底工程与协作协议 | Agent 只读摸底 + 人确认权限归属 |
| ③ | 规划互补，定架构与边界 | 两个 Agent 互挑 + 人定架构 |
| ④ | 继承规则，只记获批差异 | 人 |
| ⑤ | 建任务与验收判据 | `acceptance-author` + 人批准冻结 |
| ⑥ | 执行：按项目规范提交与交接 | `evidence-bound-executor` |
| ⑦ | 分级核验 | `evidence-led-reviewer`（个人项目由独立窗口读真实 diff） |
| ⑧ | CI 门 | 自动化，在独立于执行窗口的固定环境运行才算见证 |
| ⑨ | 我裁决 | 人（无自动触发器） |
| ⑩ | 结账与欠账入库 | 人 |
| ⑪ | 发布反馈回流 | 自持发布由人核对，团队部署由 Agent |

写这份表时的形态里，①和⑨是仅有的两个没有自动触发器的环节，靠人想起来——而它们恰好是防止判据本身写错的两道关。这个结构性事实和步数无关：**无论流程简化成几步，「开工前想清楚」和「最后自己裁决」这两件事都没有自动触发器。**

变更账本里 2026-08-08 那行写的「走完十格」是当时的口径，那时还没有第⑪步。账本是历史记录，不追溯改写。

## 验证到什么程度

**这里不设状态词。** 留在仓库里的就是还没被判死的；判断为不需要的直接删掉，理由记进变更账本。位置本身就承载了这个信息，不另设一套标签——**同一个事实存在于多处可独立编辑的地方，漂移是静默的**，而手工维护的状态标签正是那种会自己变错、且出错时没有任何东西会失败的东西。

下面每条写的是**还没有被证明的那一半**。

- `acceptance-author` / `evidence-bound-executor` / `evidence-led-reviewer` —— 三个交付 Skill 有完整证据链，见下一段。仍未测的是触发准确率。
- `deploy-to-self-managed-server` —— 九条判据来自两次独立上线的交集，其中第 9 条是两次实现都漏掉、靠清单比对才浮出来的。但**清单式 Skill 本身尚未在下一个项目触发过**；底层机制的证据不等于 Skill 的复用与触发证据。
- `project-doc-system` —— 脚手架、索引门禁与负向控制已在隔离临时项目跑通，并对两个真实项目做过只读探测，但**没有任何项目按它建起过完整文档体系**。「文档体系活下来了」要几个月和多次需求变更才验证得了。
- `thinking-toolkit` —— 2026-08-25 新增。真实调用只有一次：用方法 02（双层解释法）解释本仓库本身，路由判断、两层结构与三样收尾都按 `SKILL.md` 执行。两项减损：调用者是作者本人，且发生在写出它的同一个会话里。
- `life-design-interview` —— 2026-08-25 新增，**零调用**。`references/life-design.md` 有一节标〔补写〕，是原始材料缺页后按同一框架补的，不是原文。

最后两个和其余五个不同源：规则不是从本人事故里长出来的，而是把一组外部方法整理成路由与边界，因此连「幸存者偏差」那条部分缓解也不适用——**它们的失效样本一个都还没有**。

三个交付 Skill 已在 `family-finance` 的 1B、2A、2B 真实批次形成完整证据链：历史会话归档能定位到各自 `SKILL.md` 的读取、紧随其后的合同冻结 / 候选实施 / 独立复核动作，以及对应合同和 candidate。三批分别经历 1、6、1 轮审查退回，判据回退均为 0；2B 真实拦下了「浏览器断言全过，但 Windows 根命令因进程清理超时退出 1」的假绿灯。这不是根据方法相似性倒推。

**删除只能由真实使用结果触发**，不能因为规则写完、脚本跑通或一次自审就删，也不能因为一时没想起来用就删。反过来，真实条件下具备可用条件却零次调用，同样是结果、不是空白——那是删除的理由。

## 已知边界

### 闭环

规则的输入全部来自同一个人的项目、窗口和记忆。这套体系可以带着完整证据链整体一致地错，而系统内几乎没有信号源能发现。唯一验证过有效的外部输入是用真实数据使用运行中的产品。

### 幸存者偏差

每条规则都对应一次被抓住的事故。没被抓住的事故不产生规则，也没有机制让它们浮出来。`blind-spots.md` 是形状级泛化，是对这条的部分缓解，不是解决。

### 执行侧依从性已有真证据，人侧仍未稳定

`family-finance` 历史归档已经证明三个交付 Skill 确实被读取并紧接着执行，这解决了「方法做过，但 Skill 包是否触发」的证据缺口。它仍不能证明每次该触发时都会触发，更不能替代人侧的第①步和第⑨步——这两步没有自动触发器，仍靠人想起来，而它们恰好是防止判据本身写错的两道关。

### 真实触发已经发生，触发准确率仍未测

三个交付 Skill 已有真实正向触发样本，而且历史用户没有逐字输入带连字符的 Skill 名称，Agent 仍读取了正确的 `SKILL.md`。但这只能证明「触发过」，没有未触发对照、误触发样本和固定任务集，仍算不出召回率与准确率。

## 不适用范围

一晚上内、单模块、可回滚且不涉及安全、数据、权限或发布的小活，验收、执行与审查 Skill 都不触发。写一句可证伪的判据、完成后检查真实 diff 即可；`deploy-to-self-managed-server` 覆盖静态站与全栈两种发布形状，不覆盖未经独立评审的数据库回滚、跨服务编排，以及本仓库未验证过的托管平台。风险高时不因改动小而跳过完整流程。
