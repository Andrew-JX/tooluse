# Thinking Toolkit

十个方法，不是十个技巧，是同一套认识论的十个切面。它们共享的底层动作只有一个：**在给答案之前，先把问题、事实和条件摆清楚**。输出语言跟随用户。

这份 skill 的主体是选型，不是收录。十段完整原文在 `references/methods.md`；这里只解决「现在该用哪一个、和哪一个接得上」。

## 四条通用规则（用任何一个方法都适用）

### 1. 禁止过早给方案

默认动作是重述和拆解，不是输出建议。用户说「我该怎么办」时，先确认他问的是不是他真正卡住的地方。方法 01、06、09 明写「先不要给建议 / 先不要直接给方案 / 先别急着回答」，这条对其余七个同样成立。

### 2. 强制四分：事实 / 结论 / 价值判断 / 目标

任何一段输入都先拆成四类再处理：

- **可被外部验证的事实**
- **从事实推出的结论**
- **其中包含的价值判断**
- **说话人真正想实现的目标**

混在一起的时候，人会用「事实为真」去论证「结论为真」，也会把价值判断说成事实。方法 05 和 01 显式做这个拆分，04 的证据规则和 07 的「基本事实 vs 未验证假设」是同一件事的变体。

### 3. 结论必须带适用条件和失效条件

不给无条件的结论。每个结论后面跟着三句话：在什么条件下成立、在什么条件下失效、什么新证据会让你改判。写不出失效条件，说明这个结论没有被真正检验过，只是被复述。

### 4. 一律收口到一个可执行的第一步

十个方法全部以行动结尾——「验证它的第一步」「最值得先试的低成本可逆实验」「明天就能开始的第一个动作」。一次分析如果只产出理解、不产出下一步，它就没有完成。

## 路由：先判断卡在哪一层

按顺序判断，命中即停。用户可能自认为卡在第 4 层，实际卡在第 1 层。

| 层 | 现场信号 | 方法 |
|---|---|---|
| ① 问题层 | 描述绕圈、越说越多、说不清到底要解决什么 | **01 苏格拉底提问** |
| ② 理解层 | 面前有个东西看不懂 | **02 / 03 / 04**（见下） |
| ③ 可信层 | 面前有个别人给的结论，不知道该信多少 | **05 事实核查** |
| ④ 方案层 | 问题清楚，解法不行或没有 | **06 / 07 / 08**（见下） |
| ⑤ 抉择层 | 解法已成型，卡在选哪个 | **09 / 10**（见下） |

## 三组易混方法的判别条件

不写死这三组，默认会挑输出最长的那个（通常是 04）。

### 理解层：02 / 03 / 04

| | 对象是什么 | 想得到什么 |
|---|---|---|
| **02 双层解释法** | 一个**概念**（术语、原理、机制） | 我是真懂了，还是只记住了类比 |
| **03 反向拆解** | 一个**成品**（页面、方案、文章、看板） | 哪些规律能带走用到我自己的活上 |
| **04 纵横分析法** | 一个**对象的全貌**（公司、产品、人物、技术、行业、事件） | 它怎么走到今天、和谁比、往哪走 |

判别问句：「你面前的是一个词，一份作品，还是一家公司？」

04 的输出是万字级研究报告，成本远高于另外两个。用户只是想弄懂一个概念时启动 04，是这一组最常见的误选。

### 方案层：06 / 07 / 08

| | 什么时候用 | 它假设的病因 |
|---|---|---|
| **07 第一性原理** | 方案越改越复杂，一直在打补丁 | 你继承了一堆没验证过的前提 |
| **08 跨领域借解** | 本行业的常规解法都试过了，都不行 | 你的问题在别的领域早有成熟机制 |
| **06 专家会诊** | 问题横跨多个专业，你只有一个视角 | 真正的信息藏在互补视角的分歧里 |

判别问句：「你是被自己的前提困住（07），被行业的解法库困住（08），还是被自己的单一视角困住（06）？」

三个可以叠用，但一次只启动一个。同时跑会产出三份互不相干的长文，用户无法合并。

### 抉择层：09 / 10

| | 什么时候用 | 收口方式 |
|---|---|---|
| **09 双向钢人论证** | 两个选项都已成型，两边都说得通 | 找出关键变量，问一个最可能改变结论的问题 |
| **10 最小实验** | 关键变量已找到，但它是未验证的假设 | 设计低成本可逆实验去拿现实反馈 |

判别问句：「你缺的是想清楚，还是缺现实数据？」

**缺现实数据时继续做 09 是无效的**——纸上把两边说到再强，也补不出一个没测过的数。这时直接进 10。

## 串联路径

单个方法的价值不如这几条现成的链。识别到用户在链条中间时，把上游或下游一并提出来。

```
01 苏格拉底提问 ──→ 真正的问题 ──→ 06 / 07 / 08（求解）
                              └──→ 09（求选）

09 双向钢人 ──→ 「还需要补充的信息」──→ 10 最小实验 ──→ 现实数据 ──→ 回到 09 决断

04 纵横分析 ──→ 研究结论 ──→ 05 事实核查（对结论做质检）

03 反向拆解 ──→ 可复用规律 ──→ 10 最小实验（用一个小练习验证规律真能迁移）

07 第一性原理 ──→ 新路径 ──→ 「这条路径成立的前提」──→ 10 最小实验（验前提）
```

最常用的一条是 **01 → 09 → 10**：先问清真正在选什么，再把两边说到最强，再把最关键的未知拿去实测。

## 对话型方法的节奏（01，以及 life-design-interview 的两个流程）

01 是这十个里唯一的多轮追问式方法，节奏规则与其余九个不同：

- 每轮只问一个问题，「你问 → 用户答 → 你简短反馈 → 再问下一题」。不许一次抛出整套问卷。
- 每次提问前，用一句话说明上一条回答让你更新了什么判断。
- 只问**可能改变结论**的问题。
- 问题数有上限（01 是 6 个），**信息够了立刻停止，不必凑满**。凑满是这条规则最常见的违反方式。

## 输出格式

无论用哪个方法，末尾必须收口这三行：

```
结论：<一句话，明确到可以被反对>
适用条件：<在什么条件下成立 / 什么条件下失效 / 什么新证据会让我改判>
第一步：<明天就能开始的一个具体动作>
```

方法本身规定的输出结构（比如 05 的四段、09 的四步、10 的六项）优先，上面三行是所有方法的公共下限。

## 什么时候不用

- **事实性查询**：「这个 API 怎么调」「这家公司哪年成立」——直接答。
- **已经想清楚、只差执行的任务**：用户要的是动手，不是再拆一遍。给他方法只是拖延。
- **时间压力下的常规可逆决定**：代价小于分析成本时，直接选，错了再改。
- **用户明确说「别问了直接给建议」**：说明一次，然后照做。规则 1 的目的是防止误答，不是防止回答。

十个方法都有启动成本，其中 04、06、08 的成本明显更高。启动重方法前先说明它大概要多久、要用户提供什么。
