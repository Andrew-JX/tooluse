### P0-1 · 新建 `tooluse/CHANGELOG.md` — 流程自己的变更账本

**为什么**：这套流程要求每个批次有契约和轮次账本，但流程自己被改过三轮，没有任何记录说明哪次改动过了什么门、依据是什么。想回答「⑦ 的 ADVISORY 规则为什么是这样」，答案现在散在几个聊天窗口里。

这是同一个病的第二次发作——上一次是独立审查拿着旧契约把已授权改动判成违约，根因同样是「事实活在对话里，没进仓库」。

**内容要求**：

文件头写两条维护规则：

```
1. 这套 skill 和交付流程的每一次改动，在这里记一行。改动和记录在同一个提交里。
2. 修剪规则：连续三个批次没有任何一次被触发过的条目，降级到 references/ 或删除，并在本文件记一行。只增不减的流程最终会重到没人遵守。
```

然后是表格，列固定为：

| 日期 | 改了什么 | 为什么（依据哪次事故 / 谁的建议） | 提出方 | 过了什么门 |

**必须回填已经发生的三轮**，日期从 `git log` 取，不要凭记忆写：

- `evidence-led-reviewer` 首次建立（P0–P3 分级、证据契约、跨工具模板）
- 新增 `acceptance-author`、`evidence-bound-executor`、`blind-spots.md`，并对 reviewer 打 8 处补丁（前置条件 / 先审判据 / 六行事实 / 全称检查 / 隔离回退 / ADVISORY / 判据错不进 P0–P3 / 最没把握的判断）
- kind + origin + categoryId 数据模型、按 kind 分组、work-skill 移植、三条新边、CI 文案区分见证与门、查询参数合并修复

回填这三行的「过了什么门」一栏，如实写当时的情况，包括「无」。不要为了好看编一个门。

### P0-2 · 跑规则冲突检查，并修掉已知的那一处

**为什么**：`acceptance-author` 第 8 条叫「判据之间不许打架」，但没人对这四份 skill 自己跑过这一条。已经能看到一处结构性死锁。

**已知冲突**：

- `evidence-bound-executor` 第 6 条：上一批没有形成获授权的冻结 candidate 时不要开始下一批；用户未授权提交时写「未收口」并等待。
- `acceptance-author` 冻结规则：先冻结 `contract SHA` 与 `baseline SHA`，再开始实现。

在一个禁止提交的批次里，这两条合起来意味着**既不能开工也不能收口**。上一批就是这个状态。

**修法**（两份文件都要改，措辞自拟但必须含这三层）：

1. 本地提交（不 push）默认视为已授权，这是三锚点的前提。
2. 确实不能提交时，用契约文件的内容哈希加绝对路径作为 contract 锚点的替代；审查方比对哈希。
3. 这种情况下批次状态封顶为「⑥完成，未收口」，⑦只能给 `ADVISORY`，不得给 PASS。

**同时**：拿 `acceptance-author` 第 8 条通读四份 SKILL.md（含 work-skill）与 `blind-spots.md`，找还有没有别的冲突。找到就在交接里列出来并给修法建议，**不要自行修**——除非那处冲突和上面这条属于同一根因。

### P0-3 · 仓库规则加保鲜机制

**为什么**：④ 的 skipWhen 是「仓库里已经有一份还准确的规则文件」，但没有任何东西验证它还准确。规则烂掉是静默的：新窗口照着烂规则干活，全链路绿灯。这个仓库和 FitMind 都已经有过文档与实现不一致的实例。

**改 `AGENTS.md`**：文件开头加一行（日期取本批实际日期）：

```
> 最后复核：<YYYY-MM-DD> · 超过 90 天或 5 个批次未复核，第④步不得跳过，必须逐条对照当前仓库事实重新确认。
```

**改 `src/data/deliveryFlow.zh.ts`** 中 `id: 'repo-rules'` 的 `skipWhen`：

```ts
skipWhen: '仓库里已经有一份规则文件，且它的「最后复核」日期还在有效期内。过期就不许跳过——规则烂掉是静默的，照着烂规则干活会全链路绿灯。',
```

### P1-1 · ⑨ 加裁决超时

**为什么**：⑨ 现在没有降级模式。如果一周不裁决，这个批次怎么办，没有定义。按晚上加周末的节奏这一定会发生。

`id: 'verdict'` 的 `pitfall` 末尾追加一句：

```
还有一头没人管：超过 14 天没裁决，这个批次要转 stale——SHA 还在，但依赖、环境和我自己的上下文都变了，必须重新核验，不能直接沿用旧证据继续裁决。
```

### P1-2 · ⑦ 的有效性来源要写对

**为什么**：⑦ 现在的文案只说了「换角色名不等于独立」（否定式）。它没说这一步为什么仍然有用。在同一台机器、同一个权限域下，身份是装不出来的——已经证伪过。但第二次阅读确实抓到过大量真实缺陷，那个效果不来自身份，来自读的人手上没有第一次的叙述。

按现在的写法，容易被读成「这一格是走过场」。

`id: 'verify'` 的 `pitfall` 末尾追加：

```
但也别把这一格当摆设：它有效不是因为身份隔离——同权限同机器装不出身份——而是因为第二次阅读的人手上没有第一次的叙述。所以真正要守的不是「换个人」，是「审查方拿到的必须是仓库事实，不是执行方的摘要」。
```

### P1-3 · 交接格式加时间分段

**为什么**：修剪规则要能执行，前提是知道每一步的成本。用户 §8 那条判据（一个批次从开工到 verdict 的墙钟时间 + 打回轮数）到今天是空的，因为两次批次都没走到 verdict。没量过就没法剪。

`evidence-bound-executor` 的交接格式模板里加两行：

```
本批墙钟时间：⑤ _ 分 / ⑥ _ 分 / ⑦ _ 分 / ⑧ _ 分 / ⑨ _ 分
打回轮数：审查退回 _ 轮 / 判据回退 _ 轮
```

### P2-1 · 新建 `tooluse/README.md` — 这个库是什么，以及它的已知边界

**为什么**：这些 skill 可能被公开、被复制到别的项目。一份不说明自己边界的规则集，比没有规则更危险——使用者会以为它覆盖的比实际多。

**必须包含四部分**：

**一、这是什么。** 四个 skill 各一行，加安装路径（`.claude/skills/` 和 `.codex/skills/`），以及不支持 skill 的工具用哪份模板。

**二、状态词的含义。** 和 `toolShares.zh.ts` 里那五个状态一致。明确写：四个自建 skill 目前全部「尚未实测」，没有在真实批次上跑过。

**三、已知边界（这一节最重要，如实写，不要软化）**：

- **闭环**：规则的输入全部来自同一个人的项目、窗口和记忆。这套体系可以带着完整证据链整体一致地错，而系统内几乎没有信号源能发现。唯一验证过有效的外部输入是「用真实数据使用运行中的产品」。
- **幸存者偏差**：每条规则都对应一次被抓住的事故。没被抓住的事故不产生规则，也没有机制让它们浮出来。`blind-spots.md` 是形状级泛化，是对这条的部分缓解，不是解决。
- **依从性未验证**：agent 侧靠 skill 自动加载，人侧的第①步和第⑨步没有任何触发器，纯靠人想起来——而这两步恰好是唯一防「判据本身写错」的两步。
- **触发准确率未测**：`description` 写坏的 skill 要么永不触发要么处处触发，两种都没量过。

**四、不适用范围。** 一晚上内、单模块、可回滚且不涉及安全 / 数据 / 权限 / 发布的小活，四个 skill 都不触发。

**约束**：这份 README 是给使用者看的，不是开发日志。不要写批次号、契约路径、和用户的对话。
