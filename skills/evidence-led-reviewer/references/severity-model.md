# P0-P3 严重度模型

本文件是严重度定义的唯一权威。已知副本只有一处：`assets/reviewer-role-prompt.md`——它要发给不支持 Skills 的 Agent，必须自包含。改这份时同步那份，别处不得再出现第三份。

## 判定顺序

先判断影响，再看发生概率。一个已可达的数据删除路径即使需要误操作，也可能高于频繁出现的轻微文案问题。

依次考虑：

1. **影响**：数据、安全、隐私、合规、核心功能、用户决策、品牌或成本。
2. **可达性**：正常路径、恶意绕过、罕见竞态、仅理论可能。
3. **爆炸半径**：单次请求、单用户、租户、全站、生产基础设施。
4. **可恢复性**：自动恢复、人工修复、需要备份、不可逆。
5. **证据强度**：已复现、静态可达、合理推断、尚未验证。

## 默认定义

### P0（致命 / Critical）

系统或核心方案根本无法运行，核心逻辑自相矛盾，或存在可达的灾难性结果，例如全站数据破坏、凭据泄露、不可逆生产事故。需要立即停工、禁用入口或回滚。

### P1（严重 / High）

存在明确且可达的漏洞，会使核心功能失效、破坏数据不变量、绕过权限/同意、造成重大隐私合规风险或显著用户流失。通常阻塞合并与发布。

### P2（一般 / Medium）

局部正确性、体验、契约、文档、可观测性或流程存在问题；影响真实但范围有限，通常有替代路径或可恢复。若违反本批 acceptance 或发布门禁，可以阻塞本批。

### P3（建议 / Low）

当前没有明确用户伤害的可维护性、清晰度、性能余量或未来扩展建议。默认不阻塞。

## 校准示例

| 情况 | 默认等级 | 校准说明 |
|---|---:|---|
| 测试脚本可能连接生产并整表删除 | P0 | 高爆炸半径且可能不可逆 |
| 直接 API 可绕过授权或同意门禁 | P1 | 安全/隐私不变量失效 |
| 并发可形成非法业务终态 | P1 | 数据不变量已可复现 |
| 核心测试断言全过但命令不退出 | P1/P2 | 若阻塞发布门禁为 P1；仅影响本地便利性可降为 P2 |
| API 文档与真实响应不一致 | P2 | 若导致资金或安全决策错误可升为 P1 |
| 注释夸大已证明范围 | P3/P2 | 仅局部注释为 P3；若用于发布/合规决策则升为 P2 或 P1 |
| 命名、抽象或未来扩展建议 | P3 | 除非已造成当前缺陷 |

## 防止滥用

- 不因“代码很丑”定 P1。
- 不因“只是一句文案”自动定 P2；欺骗用户授权或影响法律告知时可能是 P1。
- 不把缺少测试本身定成固定等级；根据未受保护行为的风险定级。
- 不把未知当安全，也不把未知当已发生。写明推断与验证缺口。
