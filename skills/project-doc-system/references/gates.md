# 文档门禁

## 为什么门禁比规则重要

规则烂掉是静默的：下一个窗口照着烂规则干活，全链路绿灯。人工复核只在有人恰好去读的时候起作用，而没人会定期通读文档。

门禁的收益结构和直觉不一样——**主要收益在引入的那一刻**。真实案例：一个 API 契约门禁被引入时，一次性清掉了 9 个文档里有、代码里没有的幽灵端点，并补上 3 个漏掉的真实端点。引入之后它变成低成本保险，偶尔拦一次。

所以判断一条门禁值不值得配，看的是「现在就跑一次，它会报出多少东西」，不是「以后每周能拦几次」。

## 可移植的形状

门禁的**形状**可移植，**内容**不可移植。测试框架、文档格式、真实来源每个项目都不一样。

### 双向集合比对

最有用的一类：把文档里声明的集合和代码里的真实集合做双向差集。

```
文档声明的 - 代码里的 = 幽灵条目（文档在撒谎）
代码里的 - 文档声明的 = 漏记条目（文档不完整）
```

适用于：API 端点、目录清单、环境变量、迁移文件、配置项、文档索引。

**必须配一个显式的例外白名单**，而不是让人绕过门禁。例外写成代码里的具名常量，附一句为什么：

```js
// Health check; infrastructure rather than part of the product contract.
const UNDOCUMENTED_BY_DESIGN = new Set(["GET /health"]);
```

没有逃生阀的门禁会被整条注释掉，那比没有门禁更糟——注释掉之后没人记得它曾经存在。

### 跨文件契约比对

两个文件里的约定必须匹配，而不匹配只在生产暴露。例如：CI 生成的标识符格式，与服务器端解析它的正则。

做法是**渲染一个合成样本再拿去匹配**，而不是比较两段字符串是否相等：从 CI 侧提取模板、把变量替换成已知形状的样例值、把渲染结果丢给另一侧的正则。这样任何一侧改了写法都会被抓到。

### 存在性与非空

清单里的路径必须存在，且不是空目录。便宜，且能抓到重构后忘记同步的情况。

## 负向控制是强制的

**一个不会失败的门禁保护不了任何东西。**

两次真实教训都是同一个形状：测试存在、测试是绿的，但它没有守住它声称保护的属性——一次是并发测试用手写锁冒充了生产路径，一次是黑盒测试根本不在默认 CI 里运行。

所以每条检查都要附一个把被守护的事实改坏的对照，并要求门禁必须报错：

```js
{
  id: "...",
  run(ctx) { /* 返回问题列表 */ },
  breaks: [
    (ctx) => /* 返回一个被改坏的 ctx */,
  ],
}
```

自检模式遍历所有 `breaks`，任何一个改坏之后仍然通过，就是自检失败。

## 必须在默认路径上

不在默认验证命令里的门禁等于不存在。接进项目的 `test` / `verify` / `check` 命令，以及 CI 的默认作业。

「需要时手工跑」的门禁，在真正需要的那一刻不会有人想起来跑。

## 门禁抓不到什么

只能守可判定的不变量。抓不到的：

- 文档描述得不准确但集合对得上
- 决策理由已经作废
- 一段规则从来没人遵守

这些只能靠复核日期和过期条件。所以门禁不是文档腐烂的完整解法，是最强的那一部分。
